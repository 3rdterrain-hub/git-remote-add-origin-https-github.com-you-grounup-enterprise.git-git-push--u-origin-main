# Security model

Every control below is enforced by the database, by an Edge Function boundary, or
by both. Each is exercised by a test in `tests/db/rls.test.ts` (50 tests) or
`tests/functions/subscription-state.test.ts` (30 tests), running against real
PostgreSQL 18.

---

## Tenant isolation

The tenant boundary is `companies.id`, carried as `company_id` on every business
table.

### Layer 1 — Row level security

RLS is `ENABLE`d **and** `FORCE`d on every table in `public`. `FORCE` matters: without
it, the table owner bypasses its own policies, which is exactly the role a migration
runs as.

Policies are generated by two audited helpers rather than written sixty times by
hand, because a hand-written policy set is precisely where one omitted table becomes
a cross-tenant leak.

```sql
-- Membership is the only source of tenant access.
create or replace function app.current_company_ids()
returns setof uuid language sql stable security definer
set search_path = public, pg_catalog as $$
  select m.company_id from company_memberships m
  where m.user_id = auth.uid() and m.status = 'active';
$$;
```

`SECURITY DEFINER` is required because these functions read `company_memberships`,
which is itself RLS-protected — a plain function would recurse into the policy that
called it. `search_path` is pinned on every one so a caller cannot shadow a table
name and redirect the lookup.

An unauthenticated request produces an empty set, so every tenant policy **fails
closed**: `company_id in (select …)` over an empty set matches nothing.

### Layer 2 — Table privileges

RLS decides which *rows* a request may see. `GRANT` decides whether the request may
touch the table at all. Migration `0012` revokes everything from `anon` and grants
it `SELECT` on exactly two tables — `plans` and `plan_prices` — so the pricing page
can render before sign-in.

A migration-time gate fails the build if `anon` can read anything else:

```
Privilege gate failed. The anon role can read: <table list>
```

The result is two independent controls. A policy mistake on any business table
still cannot expose data to the public API, because the anonymous role holds no
privilege on it at all.

### Layer 3 — The structural tenant guard

RLS alone does **not** prevent a user who legitimately belongs to two companies from
attaching company A's estimate line to company B's estimate version: both
`company_id` values pass their policies.

`app.enforce_tenant_parent` closes that gap by comparing the child's `company_id`
against the parent's, and is attached to every child table carrying both:

```
Tenant boundary violation: estimate_line_items row belongs to company A,
but its parent estimate_versions <id> belongs to company B
```

This case is tested explicitly, with a fixture user who really is a member of both
companies.

### Layer 4 — The coverage gate

Migration `0011` fails if any table in `public` lacks RLS:

```
RLS coverage gate failed. Tables without row level security: <table list>
```

Adding a table without a policy breaks the build rather than shipping open. A
`rls_coverage` view reports the state operationally.

## Authorization

Access is granted through exactly one path: an active row in `company_memberships`
linking a user to a company under one role.

| Role | Tier | Summary |
|---|---|---|
| Owner | 4 | Everything, including billing |
| Administrator | 3 | Company, users, libraries, estimating, projects, audit |
| Chief Estimator | 3 | Approves and issues estimates, approves library changes |
| Senior Estimator | 2 | Full estimating including senior review sign-off |
| Estimator | 1 | Builds estimates, accepts AI findings at estimator tier |
| Project Manager | 2 | Schedule, cost, change orders, field production |
| Superintendent | 1 | Daily reports, installed quantities, production actuals |
| Foreman | 0 | Field production for assigned work |
| Accountant | 1 | Job cost, billing, financial reporting |
| Sales | 0 | CRM and proposals; reads estimates, cannot change pricing |
| Viewer | 0 | Read-only |

**Approval tier is separate from permission.** A user may hold `estimates.write`
and still be unable to clear a senior review, because the gate requires tier 2.

Permission checks run through `app.has_permission()` in the database, including
inside Edge Functions, so an endpoint cannot authorize something RLS would refuse.
Wildcards are honored only as the whole-role grant `*` — there is no `estimates.*`
prefix matching, because partial wildcards make it easy to grant more than intended.

### Segregation of duties

- A requester cannot approve their own request.
- A decider must hold the required approval tier.
- A company must always retain at least one active owner.

All three are triggers. No administrative mistake or application bug can bypass them.

## The audit ledger

`audit_events` is append-only. `UPDATE` and `DELETE` raise:

```
Table public.audit_events is append-only; UPDATE is not permitted.
```

The trigger fires regardless of privilege, so the ledger cannot be rewritten by a
user, an administrator, or a superuser. Corrections are appended as new events.

Every governed table carries a row-level audit trigger recording the full prior and
new state as `jsonb`, the actor, and the time. A no-op update writes nothing —
`updated_at` is excluded from the comparison, because the `set_updated_at` trigger
has already stamped it and including it would make every no-op look like a change.

This is what makes the configurability promise answerable as a query: *who changed
this production rate, when, from what, to what, and which estimates use which version.*

## AI governance (RULE-008)

An AI agent may read documents, propose scope, quantities, conflicts and risks, and
explain results. It may not compute an authoritative price and it may not write to
an approved record.

| Control | Enforcement |
|---|---|
| No agent can be given write authority | `check (default_authority <> 'autonomous')` on `ai_agents` |
| A finding cannot be born accepted | `check (state = 'proposed' or reviewed_by is not null)` |
| A factual finding must cite a source | `check (… or jsonb_array_length(citations) > 0)` |
| Only an identified human may accept | Trigger comparing `reviewed_by` to `auth.uid()` |
| The accepter needs the permission | Trigger checking `ai.accept_findings` |
| AI output never auto-accepts into an estimate | Engine approval gate floors it at estimator review |
| Calibration proposes, never edits | `production_calibrations` requires approval; minimum sample of 3 |

Acceptance is permanently attributed, so the provenance chain stays intact:
*document → finding → accepted by → estimate line.*

## Estimate integrity (RULE-009)

Once a version is `approved`, `issued`, `awarded` or `lost`, its priced content is
frozen. Only the fields recording what happened *to* it afterwards may change:

```
Estimate version <id> is issued and immutable (RULE-009);
field "direct_cost" cannot change. Create a new version instead.
```

An issued version can move forward to `awarded`, `lost` or `archived`, but never
back to `draft`. `app.revise_estimate_version()` is the sanctioned path: it copies
the lines, re-points parent references at the copies, and requires a stated reason.

## Payment security

### No card data, ever

The database holds Stripe identifiers, the plan, the status, the period and the
payment method **brand and last four digits for display**. No PAN, no expiry, no
CVC, no token that could be replayed. Card details are collected by Stripe Checkout
and never traverse GrounUp's frontend or database.

### Entitlement comes only from verified webhooks

There is **no INSERT or UPDATE policy** on `subscriptions` or `entitlements` for
`authenticated`. Those rows are written exclusively by the `stripe-webhook` function
using the service role. This is the structural enforcement of *never trust a browser
redirect to activate paid access* — a tenant role has no path to write them at all,
which the tests confirm directly.

### Signature verification precedes parsing

The raw request body is read as text and verified before it is treated as an event.
Anyone can POST JSON to a public URL; the signature is the only thing distinguishing
Stripe from an attacker granting themselves an enterprise subscription. A bad
signature returns 400, telling Stripe not to retry.

### Exactly-once processing

`stripe_events.id` is Stripe's own event id and the table's primary key. The webhook
claims the event with an upsert that ignores duplicates:

- **New event** → claimed, processed, marked `processed`.
- **Replay** → primary key collision → 200 with `duplicate: true`, nothing applied.
- **Failure** → marked `failed`, 500 so Stripe retries.

### The browser cannot influence what is charged

`create-checkout-session` accepts a plan id and an interval, and nothing else. The
Stripe price is resolved server-side from `plan_prices`. A tampered request can only
ever produce a checkout for a plan GrounUp actually sells:

- unknown plan → rejected
- retired plan → rejected
- non-public plan (the $0.01 partner tier) → rejected as not self-serve
- unknown interval → falls back to monthly rather than failing open

### Entitlement is not authorization

```sql
app.can_use(company, feature, permission)
  := app.has_entitlement(company, feature) and app.has_permission(company, permission)
```

A company can be entitled to `projects` while the signed-in user has no
`projects.write`. Paying for a feature is never a permission, and the UI uses the
distinction to tell "upgrade your plan" apart from "ask your administrator".

### Grace, not cliffs

A `past_due` account keeps working through Stripe's dunning window rather than
cutting a contractor off mid-bid; Stripe cancels if it stays unpaid. Entitlement
carries `valid_until` set three days past the paid period, so a *delayed* webhook
cannot lock a customer out of work they have paid for.

## Secrets

| Secret | Where it lives | Never |
|---|---|---|
| Supabase anon key | frontend bundle (public by design) | — |
| Supabase service role key | Edge Function environment | any `VITE_` variable |
| Stripe secret key | Edge Function environment | frontend, database, logs |
| Stripe webhook signing secret | Edge Function environment | frontend |
| AI provider keys | Edge Function environment | frontend |

`stripeClient()` rejects a key beginning `pk_`, so a publishable key pasted into the
secret slot fails loudly at startup rather than silently at the first charge.

CORS is allow-listed rather than `*`, because these endpoints act on an
authenticated session and start payments.

## What is not covered

Stated plainly rather than implied:

- **No penetration test** has been performed.
- **Storage bucket policies** are specified in the deployment runbook but are created
  through the Supabase dashboard or CLI, so they are not covered by the migration tests.
- **Rate limiting** relies on Supabase's platform defaults; no application-level
  throttling exists on the Edge Functions.
- **The AI document pipeline is not wired to a model.** Its governance is complete
  and tested; the ingestion and inference path is not built.
- **MFA and SSO** appear in the settings UI as configuration surface. Enforcement
  depends on Supabase Auth configuration, which is outside these migrations.
