# Architecture

## The load-bearing decision

Everything else in this system follows from one choice: **the arithmetic is
deterministic and the intelligence is advisory.**

```
Documents ──▶ AI agents ──▶ Findings (cited, inert)
                                  │
                          human approval gate
                                  │
                                  ▼
               Governed catalog ──▶ Deterministic engine ──▶ Price
                                                  │
                                          AI explains it
                                                  │
                                          Human approves
```

An AI agent reads drawings, classifies sheets, extracts quantity candidates,
compares revisions, and flags conflicts and missing scope. It never computes an
authoritative price and it never writes to an approved record. The engine, given
the same inputs, produces the same number on every machine, forever.

This matters commercially, not just architecturally. A contractor can defend an
estimate line to an owner because the derivation is inspectable arithmetic over
recorded rates — not the output of a model that cannot be re-run.

## Layers

### 1. `packages/engine` — the deterministic estimating engine

Pure TypeScript, no dependencies, no I/O, no clock, no randomness. It is the only
place authoritative numbers are produced — prices, volumes and, since the
critical path engine, schedule dates and float.

| Module | Responsibility |
|---|---|
| `numeric.ts` | Half-away-from-zero rounding corrected for binary error; every scale the engine uses |
| `units.ts` | Units, dimension families, and BCY/LCY/CCY conversion via a bank pivot |
| `quantity.ts` | Measured → adjusted → waste/loss → gross, and bid quantity reconciliation |
| `production.ts` | Condition modifiers by target, theoretical/practical/recommended production, controlling resource, duration |
| `resources.ts` | Loaded labor rate, crew cost with overtime premium, equipment rate hierarchy, fuel |
| `trucking.ts` | Trip-based haul cycle, fleet balance, cut/fill balance in correct volume states |
| `surfaces.ts` | Surface comparison, cut/fill grids, cross sections, progress to grade |
| `assemblies.ts` | Recipe expansion through nested assemblies, cycles refused by name |
| `materials.ts` | Waste, order multiples, supplier minimums, freight and tax |
| `pricing.ts` | Cost buckets, parallel and stacked markup, regional factor, escalation |
| `confidence.ts` | Verification status, 0–100 confidence, contingency banding, approval gates |
| `estimate.ts` | Orchestration: one line end to end, and the estimate rollup |
| `snapshot.ts` | The library rows that priced a version, copied so the figure stays reproducible |
| `scenarios.ts` | Named low/base/high cases and single-driver sensitivity |
| `overrides.ts` | A person's figure recorded beside the engine's, never replacing it |
| `portable.ts` | Versioned export and import; a round trip reproduces every derivation |
| `calendar.ts` | Working-day arithmetic on integer epoch days: working weeks, holidays, spans |
| `schedule.ts` | Critical path: forward and backward pass, four link types with lag, total and free float, baseline variance |

Because it has no dependencies, the engine runs unchanged in the browser, in a
Node service, in an Edge Function or in a test. The web application imports it
directly, which is why the marketing page can show a genuinely computed estimate.

### 2. `supabase/migrations` — the governed data layer

56 ordered migrations. The important structural choices:

- **`company_id` is the tenant boundary** on every business table, with RLS
  policies generated by two audited helpers rather than hand-written sixty times.
- **A build-time gate** (`0011`) fails the migration if any table in `public` lacks
  RLS, so adding a table without a policy breaks the build rather than leaking.
- **A second gate** (`0012`) fails if the anonymous role can read anything other
  than the public plan catalog.
- **Library records are three-tier**: global seed (read-only to every tenant),
  enterprise-group standard, and company override. This is what lets a holding
  company publish a corporate library while a subsidiary keeps local rates.
- **Generated columns** compute what must never drift from its inputs — the
  burdened labor rate, the production daily rate, the achieved field rate.
- **Triggers enforce what constraints cannot**: version immutability, tenant
  parentage, approval authority, AI acceptance, last-owner protection.

### 3. `supabase/functions` — the privileged server boundary

9 functions — six for billing, the governed document analyst, the public API
gateway and a health endpoint — plus shared helpers. Two Supabase clients are
used deliberately:

- The **user client** carries the caller's JWT, so its queries are subject to the
  same RLS the browser is. Permission checks run through it, which means a function
  cannot authorize something the database itself would refuse.
- The **admin client** uses the service role and bypasses RLS. It is used *only*
  to write billing state from verified Stripe webhooks.

The webhook's state machine lives in `_shared/subscription-state.ts` as a pure
function with no Deno imports, which is what makes billing unit-testable without
a Stripe account or a live database.

### 4. `apps/web` — the application

React 19, Tailwind 4, shadcn/ui components vendored on Radix primitives, routed
with React Router and split per route. The marketing landing page loads eagerly;
everything behind authentication is a separate chunk.

## Request paths

**Reading business data** — browser → Supabase PostgREST → RLS evaluates
`app.is_member(company_id)` and the relevant permission → rows.

**Pricing an estimate** — the engine runs client-side against catalog records the
user is already permitted to read. No round trip, and the derivation is inspectable
in the UI because the engine returns every intermediate value.

**Starting a subscription** — browser sends only `{companyId, planId, interval}` →
Edge Function verifies the JWT, checks `billing.manage` through the *user* client,
resolves the real Stripe price from the governed catalog, and creates the session.
Nothing the browser sends can influence what is charged.

**Activating paid access** — Stripe → webhook → signature verified → event id
claimed in `stripe_events` (the primary key is the idempotency barrier) → tenant
resolved from data GrounUp itself wrote → pure state machine derives the rows →
service role writes `subscriptions` and `entitlements`. A success redirect grants
nothing.

## Why these choices

**Why a client-side engine rather than a pricing service?**
Latency and inspectability. An estimator adjusting a production rate wants the
number to move as they type, and wants to see the derivation. The engine is
dependency-free and deterministic, so the same code can later run server-side for
API consumers without a second implementation to keep in sync.

**Why generated columns instead of application-computed values?**
Because a burdened rate that can be edited independently of its base wage will
eventually disagree with it, and nobody will know which is right.

**Why is the audit ledger a table with a trigger, rather than logs?**
Because the configurability promise is "you can change a production rate, and
GrounUp will know who changed it, when, from what, to what, and which estimates
use which version." That is a query, not a log search.

**Why three library scopes rather than copying the seed per tenant?**
Copying 4,671 records per company makes the shipped benchmark diverge immediately
and makes cross-tenant comparison meaningless. A read-only global tier keeps the
benchmark stable and makes "your rate vs the benchmark" a real question.

**Why keep fuel out of `totalEquipmentCost`?**
RULE-001. A reader must always be able to see what the iron cost and what the
diesel cost. Blending them hides the single most volatile input in heavy civil.

## What is deliberately not built

Named honestly rather than implied:

- The AI agents are **registered and governed** — the `ai_agents` registry, the
  `ai_findings` channel, the acceptance trigger and the review UI are complete and
  tested — but no model is wired to a document pipeline. The findings shown are
  representative of what the agents produce.
- **Procurement, fleet, scheduling, HSE, GIS and machine control** have their
  entitlement flags and their place in the architecture, but no screens.
- **Proposal PDF generation** has its data model and a preview action; the renderer
  is not implemented.

See [`TEST-REPORT.md`](TEST-REPORT.md) for the complete list of what is proven,
what is implemented but untested, and what is scaffolded.

## Layers added after the first release

**`packages/pdf` — document rendering.** Proposals, pay applications and reports
are rendered to PDF by a writer with no dependencies. That is a deliberate
choice on a path that handles contract values: it runs unchanged in the browser,
in Node and in a Deno Edge Function, so a document rendered on screen and one
rendered by a scheduled job are byte-identical, and the same input always
produces the same bytes — which is what lets a certified pay application be
hashed and compared.

**`supabase/functions/_shared/connectors` — the adapter framework.** Every
external system reaches GrounUp through one `ConnectorAdapter` interface, and
the runtime around it owns retry, failure classification, idempotency and run
recording so no adapter implements them slightly differently. Adapters receive
an injected `HttpFetch`, which is what makes them testable against recorded
payloads with no credentials.

**`supabase/functions/_shared/ingestion` — the document pipeline.** A drawing set
is split, inspected for a text layer, and classified sheet by sheet against the
National CAD Standard numbering convention *before* any model is called. A
regular expression over a numbering convention is cheaper than a model and
cannot be confidently wrong, so everything it establishes is handed to the model
as a fact rather than asked as a question. OCR is an injected interface reached
only for pages that genuinely need it.

**`supabase/functions/api` — the public gateway.** The authorization decision is
a pure function in `_shared/api/gateway.ts`, so the checks that stand between an
API key and another company's data are unit tested without a deployment. The
gateway's route table is the single source of the OpenAPI specification, which
`npm run verify` regenerates and fails on drift.

**The semantic layer.** `metric_definitions` holds one governed definition per
metric — global rows a company may override, exactly as the three-tier library
scope works everywhere else — and four `reporting_%` views compute them. Every
view sets `security_invoker`, and a migration-time assertion refuses to apply if
one does not, because a view that runs as its owner reads past RLS on every
table beneath it.
